# hah 测试标准

- 状态：Locked
- 版本：v1
- 锁定日期：2026-04-17
- 作用：定义仓库级测试方法与最小执行基线。
- 关联文档：
  - `docs/query-design.md`
  - `docs/path-design.md`
  - `docs/binding-query-design.md`
  - `docs/binding-body-design.md`
  - `docs/errx-design.md`
  - `docs/resp-design.md`
- 变更规则：公开行为变化时，先改对应设计文档，再补失败测试，再改实现。

## 1. 文档锁版规则

- `docs/` 下的设计文档是当前版本的公开行为基线。
- 本文档只定义“怎么测”；具体行为以对应设计文档为准。
- 若本文与专项设计文档冲突，以专项设计文档为准。
- 根包 `hah` 作为 facade，必须保持与 `reqx` / `resp` 的底层契约一致，不得额外发明默认行为。

## 2. 核心原则

### 2.1 公开契约优先

测试优先锁定：

- 公开 API
- 公开错误语义
- 文档承诺的默认行为
- 已知 bug 的回归

测试不以覆盖率数字、内部 helper 分支数或实现细节为目标。

### 2.2 TDD

仓库里的 TDD 要求固定为：

1. 新增行为时，先写或先调整行为测试。
2. 修 bug 时，先写能稳定失败的回归测试。
3. 先看到旧实现失败，再修实现，再让测试变绿。
4. 测试表达的是“对外契约”，不是“当前实现怎么写”。

### 2.3 KISS / DRY

- 用最少、最直接的用例证明行为。
- 同一契约只在一个层级直接验证一次。
- 只有在公开入口无法清晰表达契约时，才考虑测内部 helper。
- 不为了“看起来更全”而堆重复矩阵。

### 2.4 稳定与可重复

测试必须避免依赖：

- 真实网络
- 真实时钟
- 随机顺序
- `sleep`
- 外部服务
- 其他偶然时序

失败信息必须能定位行为差异，而不是只报宽泛的 `got != want`。

## 3. 什么算合格测试

合格测试至少满足：

- 直接证明某个公开行为成立
- 在错误实现存在时会失败
- 同时覆盖成功、失败、边界三类场景中的至少一种
- 对 bugfix，额外覆盖失败复现和修复后结果

以下情况不计入验收：

- 只调用函数，不断言结果
- 只追求覆盖率
- 主要依赖私有字段、私有 helper 或内部步骤
- 断言过宽，多个错误实现都能通过
- 同一契约在多个层级重复验证

## 4. 每篇设计文档的最小测试形状

每篇锁版设计文档都必须对应一组最小黑盒基线，至少覆盖：

1. 成功路径
2. 失败路径
3. 边界条件
4. 已知回归风险或最容易误实现的行为

补充规则：

- “代表性用例”优先于“穷举矩阵”。
- 一条公开规则只需要一组最能证明它的测试，不要求把同一语义拆成大量近似 case。
- 解析器、归一化器、错误收敛器和输入边界改动，应额外评估 `-count=100` 或 fuzz。

## 5. 仓库级执行基线

完成实现前至少运行：

```bash
make ci
```

若改动涉及核心 HTTP 边界、共享状态或并发路径，再运行：

```bash
go test ./... -race
```

若改动涉及解析、归一化、错误收敛或输入面，再评估是否需要：

```bash
go test ./<touched_pkg> -count=100
go test ./<touched_pkg> -run=^$$ -fuzz=Fuzz -fuzztime=10s
```

规则：

- `-count=100` 不要求每次全仓执行，但受影响核心包必须显式判断是否需要。
- fuzz 不是每次都必须新增，但高风险输入面改动必须显式判断“需要”或“不需要”。
- 该判断可以记在 PR 描述或评审备注里，不要求写进测试文件注释。

## 6. 包级验收指针

### 6.1 根包 `hah`

至少验证：

- facade 是否正确暴露 `reqx` / `resp` 的稳定入口
- facade 是否保持底层契约一致
- README 或示例中承诺的主路径是否有代表性支撑

### 6.2 `reqx`

至少验证：

- `Query(...)` 服从 `docs/query-design.md`
- `Path(...)` 服从 `docs/path-design.md`
- `BindQuery(...)` 服从 `docs/binding-query-design.md`
- `BindBody(...)` 服从 `docs/binding-body-design.md`
- 文档里引用到但尚未单独锁版的 `RequireBody(...)` 组合语义，至少按相关设计文档中的组合场景覆盖

### 6.3 `errx`

至少验证：

- `HTTPError`、`Violation` 和共享常量的公开语义
- 标准化规则
- 错误链语义
- defensive copy 语义

具体行为以 `docs/errx-design.md` 为准。

### 6.4 `resp`

至少验证：

- 成功 JSON 写回
- Problem JSON 错误写回
- 回退与写失败边界
- 头部所有权

具体行为以 `docs/resp-design.md` 为准。

## 7. 评审清单

后续审查时至少确认：

- 是否先更新了对应设计文档
- 是否先写了失败测试或回归测试
- 是否直接测了公开行为
- 是否覆盖了成功、失败、边界
- 是否避免了白盒噪音和重复规格
- 是否运行了 `make ci`
- 是否对 `-race`、`-count=100`、fuzz 做了合理判断
