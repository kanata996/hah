# hah 测试标准（TDD / KISS / DRY）

本文档定义 `hah` 仓库的项目级测试质量标准。
评审测试质量时，以“是否锁住公开行为与已知回归”为主，不以覆盖率数字、注释清单或白盒分支数为主。

适用范围：

- 根包 `hah`
- `bind`
- `reqx`
- `errx`
- `resp`
- 未来新增的公开包与公开 HTTP 边界能力

## 1. 核心原则

### 1.1 测试目标

单元测试的目标是：

- 锁住公开行为
- 锁住真实 bug 的回归
- 在重构时提供稳定安全网

单元测试的目标不是：

- 追求覆盖率数字本身
- 证明内部实现“走过了哪些分支”
- 用大量近似用例堆叠“看起来很满”的测试集

### 1.2 TDD 原则

TDD 在本仓库里的要求如下：

1. 新增公开行为时，优先先写或先调整行为测试。
2. 修 bug 时，必须先补能稳定复现问题的回归测试。
3. 先看到旧实现失败，再修实现，再让测试变绿。
4. 变更完成后，测试应表达“公开契约是什么”，而不是“当前实现怎么写”。

只改实现、不补回归测试，不算完整修复。

### 1.3 KISS / DRY 原则

测试设计必须同时满足：

- `KISS`：用最少、最直接的用例证明行为，不引入无价值注释、无价值 helper 测试、无价值矩阵。
- `DRY`：同一契约只在一个层级表达一次；重复的规格矩阵要提炼成共享 contract 或 table-driven 测试。

当“多写几个测试”只是让测试文件更长，而没有增加新的行为证据时，应停止继续补测试。

## 2. 什么是合格测试

合格测试必须满足：

- 直接证明某个公开行为或必要的稳定内部契约成立
- 在错误实现存在时会失败，在修复后会通过
- 不依赖网络、真实时钟、随机顺序或外部环境偶然性
- 失败信息能定位行为差异，而不是只报 `got != want`

至少应优先覆盖：

- 成功路径
- 失败路径
- 边界条件或退化条件

对于 bugfix，还应覆盖：

- 旧实现的失败复现
- 修复后的正确结果
- 同类问题最关键的不应发生行为

## 3. 什么是不合格测试

以下情况不计入验收：

- 只调用函数，不验证可观察结果
- 只验证覆盖率，不验证行为
- 断言过宽，多个错误实现都能误通过
- 主要依赖实现细节、私有 helper、内部分支，而不是对外契约
- 用 sleep、时序巧合、日志顺序巧合来判断结果
- 公开包装函数没有直接测试，只靠下层 helper 间接“带到”
- 同一契约在多个层级重复测试，导致维护成本明显上升

### 3.1 关于内部 helper / 白盒测试

默认规则：

1. 先测公开入口。
2. 只有在公开入口无法清晰、稳定、低成本地表达契约时，才单独测内部 helper。

允许单测内部 helper，必须同时满足：

- 该 helper 承载稳定内部契约，而不是暂时实现细节
- 通过公开入口表达会明显更差、更脆弱或更不清晰
- 单测该 helper 的维护成本低于公开入口等价测试

否则，按白盒噪音处理。

## 4. 文件注释与清单

测试文件头部的“测试清单”不是强制要求。

规则如下：

- 如果清单能明显帮助评审快速理解文件职责，可以保留。
- 如果清单只是重复测试名、重复文档、容易过时，应该删除。
- 注释不能替代测试本身；真正的证据永远是可执行测试。

换句话说：

- 不因为“仓库习惯”强制每个 `*_test.go` 写清单
- 不把 `[✓]` / `[x]` 注释当成验收标准
- 不为了维护清单而牺牲 KISS

## 5. 什么时候该继续补测试

只有以下情况，才建议继续补测试：

1. 新增了公开 API 或公开语义。
2. 修复了真实 bug，需要补回归测试。
3. 做了较大重构，发现现有公开行为缺少直接保护。

以下情况通常不需要继续补：

- 当前公开契约已经有成功、失败、边界三类测试
- 最新 bugfix 已经有回归测试
- 再补只会增加白盒覆盖或重复矩阵
- 唯一理由是“把覆盖率再抬高一点”

## 6. 仓库级执行基线

至少应运行：

```bash
make ci
go test ./... -race
```

若变更触及核心 HTTP 边界包、错误收敛逻辑、共享状态或并发路径，还应至少运行：

```bash
go test ./<touched_pkg> -count=100
```

若变更触及解析、编码、归一化、错误收敛、query/path/header/body 输入面，还应评估是否需要 fuzz：

```bash
go test ./<touched_pkg> -run=^$$ -fuzz=Fuzz -fuzztime=10s
```

说明：

- `-count=100` 不要求每次对全仓执行，但对受影响核心包应执行。
- fuzz 不是每次都必须新增，但解析器、归一化器、边界编码逻辑的高风险改动必须显式判断“需要”或“不需要”。
- 该判断记录在 PR 描述或评审备注即可，不要求写进测试文件头注释。

## 7. 各包最小验收范围

### 7.1 根包 `hah`

至少覆盖：

- facade 是否正确暴露 `bind` / `reqx` / `resp` 的核心入口
- 根包对底层包的包装是否保持契约一致
- README 中承诺的示例路径是否有代表性支撑

### 7.2 `bind`

至少覆盖：

- path/query/header/body 的独立绑定
- `Bind(...)` 的绑定顺序与覆盖规则
- 空 body、错误 `Content-Type`、超大 body、未知字段
- DTO 已有值时的保留语义
- 绑定失败时的已写入值保留规则
- 单源 API 与综合 API 的一致性

### 7.3 `reqx`

至少覆盖：

- `Normalize()` 在字段校验前执行
- `RequestValidator` 在字段校验前执行
- 校验错误字段名映射到请求 tag，而不是 Go 字段名
- `InvalidRequest` / `Violation` 的公开错误语义
- `RequireBody` 与组合入口的 body-required 契约
- 公开 builder 的稳定契约

说明：

- 优先测试 `Path` / `Query` / `BindAndValidate` / `Validate` 的公开行为
- 不要求为私有 helper 单独补“分支覆盖测试”

### 7.4 `errx`

至少覆盖：

- `HTTPError` nil 接收者的安全默认值
- `Status` / `Code` / `Title` / `Detail` / `Errors` 的标准化规则
- `Error` / `Unwrap` 的 cause 语义
- 公开 detail/errors 的防御性切片拷贝
- 构造器与快捷构造器的稳定输出

### 7.5 `resp`

至少覆盖：

- `OK` / `Created` / `NoContent`
- `JSON` / `JSONBlob`
- `WriteError(...)` 的错误收敛与 problem JSON 写回
- `errx.HTTPError` 的对外响应契约
- `nil writer`、非法状态码、无响应体状态、已开始写出等退化路径
- 内部 cause 不泄漏到公开响应
- 5xx 与错误写回失败日志的契约

## 8. 评审清单

后续审查测试质量时，至少逐项确认：

- 公开行为是否有直接测试
- 改动点是否同时覆盖成功、失败、边界三类场景
- bugfix 是否先有回归测试
- 是否存在只测 helper、不测公开入口的问题
- 是否存在明显重复矩阵而未抽象的问题
- 断言是否具体、失败信息是否可定位
- 测试是否依赖时序、随机、外部环境或未恢复的全局状态
- 是否需要 `-race`、`-count=100` 或 fuzz
- 如果公开契约变化，README / docs / CHANGELOG 是否需要同步

## 9. 当前仓库推荐做法

- 新增公开能力时，先补行为测试，再补实现。
- 修 bug 时，先补回归测试，再修实现。
- 优先写黑盒行为测试；只有在确有必要时才写白盒 helper 测试。
- 对重复规格矩阵优先提炼共享 contract，而不是复制粘贴。
- 当前测试已经足以保护公开契约时，停止继续补测试，不为覆盖率继续加例子。

若未来 CI 加入更强的稳定性检查，应以 CI 为最低门槛；但本文档定义的行为验收标准仍然优先于覆盖率数字。
